# Changelog

## 0.1.3

This release is faster, and it uses less memory on large profiles. More outputs are now the same as the outputs of XProf 2.23.2. The release binary is smaller, and PyPI has wheels of the binary.

### Packages

- The Linux release binary is 21.5 MB. Before, it was 27.1 MB. Marin can put the binary without xz in its Iris bundle of 25 MiB. The binary has no debug symbols. Its TLS uses ring, not aws-lc. The compiler makes the network and cloud crates small, and it makes the other crates fast. On an 80 MB JAX CPU profile, the speed and the output do not change. The `profiling` profile keeps its line tables.
- Each release also puts wheels on PyPI. `pip install xprof-rs` puts the binary on the `PATH`. The wheel has no Python code. Thus a tool such as Iris can install xprof-rs with its Python packages, and the uploaded bundle does not contain the binary.
- The source keeps the files of the user interface as plain files in `ui/`. The build compresses the files into the binary. The served files do not change.

### Output that is now the same as XProf

- The trace viewer writes the times as XProf does. XProf writes `%.17g` of the time in microseconds, for example `660215.41857099999`. Before, xprof-rs wrote six decimal places, for example `660215.418571`. The two texts have the same value, but the bytes were different. The response is approximately 4% larger, and its first render takes approximately 5% more time.
- The `plane_regex`, `event_regex` and `trace_matchers` options of the CLI find text as Python `re` does. Before, they used the syntax of Rust. Thus `$` also matches before a final new line, `(?i)` uses the case rules of Python, and look-around, back references and conditional groups are available. A bad pattern gives the error message of Python, for example `missing ), unterminated subpattern at position 0`.
- When a CLI command returns an empty list in the `dict` format, it prints nothing, as XProf does. Before, it printed `[]`.
- When a number is halfway between two short texts, the CLI writes the text with the even last digit, as Python does. For example, 616143034000 / 8192 gives `75212772.70507812`. Before, xprof-rs wrote `75212772.70507813`.
- For all option values, such as numbers, `True` and `None`, the CLI gives the same output and errors as XProf. Before, xprof-rs changed many of these values to text, or it gave a different error. Fire reads `1,2` and `(1,)` as tuples, `{1,2}` as a set and `{a:1}` as a dict, and xprof-rs now keeps these kinds apart from lists. For example, `--limit=None` gives the error `'>' not supported between instances of 'NoneType' and 'int'`, and `--output_type=1.5` gives `Unsupported option type for key 'type': <class 'float'>`. An error about an option value now occurs at the same step as in XProf. Thus an error about the session can occur first.
- `compute_utilization` and `get_kernel_utilization` open each trace file before they read the profile. When a file is a broken link or you cannot read it, they give the `PATH_ERROR` of XProf. The error text is the text of Python, for example `[Errno 2] No such file or directory`. Before, they gave an `INTERNAL_ERROR` with the text "no data returned".
- A direct trace file gives no utilization data when its file name does not contain the first host name. A profile found with `--logdir` does not use this check. For example, host `worker-0` in `host.xplane.pb` gives no data as a direct file, but it gives utilization data with `--logdir`. If a session has no utilization counters, `--logdir` returns an empty device list with `SUCCESS`.
- When an event or a stat has no metadata, the CLI writes its ID as a signed number, as XProf does. For example, it writes `-1`, not `18446744073709551615`.
- To find an event name that is a number, the CLI uses the rules of `str.isdigit` in Python. Thus `²` and `٣` are numbers, and `½` is not a number.
- The normalized times of the op statistics change a double to an integer as XProf does on x86-64. A value that is too large gives 2^63, and a negative value wraps. Before, a very large time scale multiplier gave a different time scale for the roofline model.
- When the `Time Scale Multiplier` stat of an op is not a double, its value is 0, as in XProf. Before, xprof-rs used 1.
- When the `_p`, `_c`, `_pt` or `_ct` stat of an event is not an integer, its value is 0, as in XProf. Thus the event connects to its producer or consumer for the groups and the flows of the trace viewer. Before, xprof-rs ignored the stat.
- When the `device_offset_ps`, `device_duration_ps`, `step_idle_time_ps` or connection stat of an event is not an integer, its value is 0, as in XProf. The connection stats are `run_id`, `queue_id`, `device_ordinal`, `core_type`, `request_id`, `queue_addr`, `id` and `iter_num`. Before, xprof-rs ignored these stats. Then a step had a different time, or the trace viewer did not show a flow.
- A `group_id` stat of the host steps that is not a signed integer gives the group 0, as in XProf.
- When the metadata plane has no `program_id` stat, the program ID of an HLO module comes from the digits at the end of its name. XProf has the same rule. Before, this failed when the metadata also had a display name. Then the op profile showed `main` and no fused operations.
- To find events by name, xprof-rs uses the name of the metadata, as XProf does, also when the metadata has a display name. This applies to memory events, threadpool regions, the roots and links of the groups, the step markers, and the framework ops of the host. Before, xprof-rs did not find these events.
- A `ThreadpoolListener::StartRegion` event starts a region when it has a `_c` stat of any type, as in XProf. Before, xprof-rs ignored the event when the stat was not an integer. Then the trace viewer did not show the region, or it showed a region from an earlier start.
- xprof-rs uses an HLO module only when C++ protobuf can parse all of its proto, as XProf does. Before, xprof-rs showed a module with a bad nested field or with text that is not UTF-8. XProf removes such a module from the module list, the op profile and the HLO tools. Text in `pbtxt` format now also accepts unknown groups, as C++ protobuf does.
- When a profile file is not a valid `XSpace`, xprof-rs extracts no HLO modules from it, as XProf does. Before, it extracted the modules from the metadata plane, for example when an event name was not UTF-8. The check of the file and the extraction occur at the same time, so the extraction takes the same time.
- `aggregate_xplane_events` rounds the average duration one time, as Python does when it divides two integers. Before, a total of more than 2^53 ps sometimes gave a different last digit in `avg_duration_ps`.
- The HTML page of the graph viewer and of the memory timeline has the same DOT text as XProf. Before, xprof-rs added a backslash before each backslash, for example in the backend configuration. xprof-rs still adds backslashes when the text has a backtick, `${`, `<!--` or `</script`, because then the text can run as a script.
- When the start time of the trace viewer is after the end time, the visible time is one instant at the start, as in XProf. This change occurs before an end time of 0 becomes the end of the trace. Before, `start_time_ms=5` with no end time showed all events after 5 ms.
- The trace viewer reads its time options as `absl::SimpleAtod` does. It accepts hexadecimal numbers after `0x`, and it removes only ASCII spaces around the number. It reads `resolution` and `unique_id` as integers first. A negative time, NaN or infinity gives the same number of picoseconds as XProf on x86-64. Before, xprof-rs returned 404 for `0x10`, and it showed different events for -1, NaN or infinity.
- A search with `search_metadata=true` shows the stack frames of the full trace, as XProf does. Before, the `stackFrames` object had only the frames of the events that the search found, with different numbers.
- A `bitcast-convert` instruction is in the category "non-fusion elementwise" only when its input and output types have the same number of bits, as in XLA. Before, xprof-rs used 8 bits for the types `s1`, `s2`, `s4`, `u1`, `u2` and `u4`. Thus a `bitcast-convert` from `s4` to `u8` had the incorrect category.
- When the overview data gives a negative number of steps, `check_host_boundness` keeps the negative number, as XProf does. Before, the number changed to 18446744073709551615, and the times were very large.

### Fixes

- Two `get_xspace_proto` commands can save the same large profile at the same time. Each command gives a full file, and on a 1.7 GB profile each takes 2.1 s. Before, one command sometimes cut the file of the other command, and it waited 19 s for the disk. Each command writes a new file, and then it exchanges the new file with the old file. The extracted HLO modules also use this write.
- The CLI finds a trace when you give only its file name in the current directory, for example `get_hosts host0.xplane.pb`. Before, the command failed with "No .xplane.pb or .xspace.pb files found".
- The server does not remove the files of a session that a download still writes, when the remote mirror is too large. Before, a long download sometimes lost its file, and the request failed with "Cannot write the mirror".
- A response of 4 GiB or more is complete when the client does not accept gzip, for example `curl` without `--compressed`. Before, the server used the gzip size field, which keeps only the low 32 bits. Thus the response was too short.
- A search of the trace viewer gives the events in the order of their levels. Thus the time delta from one event to the next can be less than zero. The delta then wraps, as in XProf. Before, a debug build of xprof-rs stopped with a panic. The output of the release build does not change.

### User interface

- Charts that did not show now show. Before, a tool sometimes got its data before Google Charts loaded its packages. Then some charts stayed empty. Examples are the charts of the HLO op stats, the heap chart of the memory viewer, and the device charts of the framework op stats. Now the interface starts after Google Charts is ready.
- The browser keeps the files of the user interface. When the page opens again, the server sends a short "not modified" response, not 1.3 MB of files. The browser also keeps its compiled scripts, so the trace viewer opens approximately 20% faster when you open it again. The page looks the same.
- The user interface is faster, and the pages look the same. On a 280 MB TPU v4 profile, the roofline model is ready in 2.6 s on a new server (before: 5.1 s). When the server has the data, it is ready in 1.6 s (before: 3.9 s). A chart draws one time when its data and its filters change, not two times. Ready means that the page draws all charts and responds to input.
- On a 280 MB TPU v4 profile, the HLO op stats page responds to input after 4.5 s. Before, it did not respond until 8.2 s. The charts show at the same time as before, after approximately 3.1 s. Google Charts makes a hidden table of all the rows of each chart for screen readers. The browser does not do the layout of these tables until they come into view. Screen readers can still read them.
- The trace viewer opens faster, and it shows the same trace. On a 280 MB TPU v4 profile, it opens in 2.0 s on a new server (before: 2.8 s). When the server has the trace, it opens in 1.8 s (before: 2.1 s). When the browser asks for the hosts of a profile with one host, the server starts to load the profile. Thus the load and the start of the trace viewer occur at the same time.
- When you zoom the trace viewer, it gets new data 200 ms after the last change of the view. Before, it waited 500 ms. On a CLIP profile, the zoomed view shows in 245 ms. Before, it showed in 540 ms.
- When you zoom the trace viewer on a 280 MB TPU v4 profile, the new view shows approximately 60 ms faster.
- When you zoom the trace viewer during a load, it gets the data for the new view after the load. Before, it kept the data of the old view until you zoomed again.

### Speed and memory

- On a 280 MB TPU v4 profile, the first request of the op statistics tools is 2% to 3% faster. The server does not do a text comparison for each event, and it checks valid text faster.
- On a 280 MB TPU v4 profile with 4 cores, the CLI commands that read op statistics are 4% to 6% faster. On an 80 MB profile, they are 1% to 5% faster. For the time span of the XLA ops on a line, xprof-rs reads only the first and the last events of the line. Before, it read the stats of all the events.
- `get_xspace_proto` removes the old file in `/tmp` before it writes the new file. On ext4, a write over a large file waits until the disk has the data. When you call the command again for the same session on an 80 MB profile, it takes 0.10 s. Before, it took 0.60 s. The first call does not change. The file does not change.
- `get_hlo_stats` does not make the statistics of the instructions in fusions, because its output does not show them. On a 280 MB TPU v4 profile with 4 cores, it takes 0.58 s. Before, it took 0.80 s. On an 80 MB profile, it takes 0.12 s. Before, it took 0.14 s.
- The CLI commands that scan all the events start with the largest lines. Before, one thread sometimes scanned all of them. On a 280 MB TPU v4 profile with 4 cores, `get_kernel_stats` takes 0.37 s, `aggregate_xplane_events` takes 0.42 s, and `list_xplane_events` takes 0.21 s. Before, they took 0.59 s, 0.58 s and 0.32 s. On an 80 MB profile, these commands and `get_avg_step_time` are 2% to 10% faster.
- When a profile has more than 5,000,000 events, `aggregate_xplane_events` uses the results of the parallel scan. Before, it scanned the profile again on one thread. On a 1.7 GB profile with 4 cores, it takes 2.2 s. Before, it took 6.4 s.
- `check_host_boundness` gets the times of the op profile from the op statistics. Before, it made the JSON text of the op profile and then read the text again. On a 280 MB TPU v4 profile with 4 cores, it takes 1.15 s. Before, it took 1.25 s. On an 80 MB profile, it takes 0.30 s. Before, it took 0.31 s.
- `get_device_information` makes only the properties of the roofline table. It does not make the rows or the programs of the steps. On a 280 MB TPU v4 profile with 4 cores, it takes 0.37 s. Before, it took 0.59 s. On an 80 MB profile, it takes 0.10 s. Before, it took 0.20 s.
- The trace viewer finds the events with a flow when it gives the flows their numbers. Before, it read all the events again on one thread. On a 1.7 GB profile with 90,000,000 events, the first request of the trace viewer takes 13.2 s. Before, it took 13.6 s.
- When a trace has more than 16,777,216 events, the trace viewer sorts the events in place. Before, it kept two copies of the events during the sort. On a 1.7 GB profile with 8 cores, the first request of the trace viewer uses 14 GB of memory and takes 11.9 s. Before, it used 22 GB and took 10.2 s. A smaller trace does not change.
- For the busy time of the TPU chips, the op statistics sort the op intervals with a stable sort. The intervals of each line are already in order, and the stable sort uses this order. On a 1.7 GB profile with 4 cores, `get_overview` takes 7.0 s. Before, it took 7.4 s. On a 280 MB TPU v4 profile, it takes 0.75 s. Before, it took 0.79 s.
- The op statistics of the TPUs make the programs of the steps from the same reads of the events. Before, the steps read each event again. On a 1.7 GB profile with 4 cores, `get_overview` takes 6.3 s. Before, it took 6.9 s. On a 280 MB TPU v4 profile, it takes 0.70 s. Before, it took 0.75 s.
- When the trace viewer finds the names of the stack frames, each thread reads a flag before it writes the flag. Before, all the threads wrote the same flags. On a 1.7 GB profile, this step takes 0.13 s. Before, it took 1.5 s.
- The legacy JSON trace of the `trace_viewer` tool keeps the first 5,000,000 events in time. For a larger trace, it now finds the time of the last kept event first, and it makes only the events up to that time. Before, it made all the events. On a 1.7 GB profile with 4 cores, it takes 14 s. Before, it took 132 s.
- The barrier times of `check_host_boundness` use the same method, and they make only the barrier events. On a 1.7 GB profile with 4 cores, `check_host_boundness` takes 9.8 s and 8 GB of memory. Before, it took 32 s and 40 GB.
- On a FUSE mount, for example `rclone mount` of a bucket, xprof-rs reads each file in order. Before, it read 4 parts of the file at the same time, and `rclone mount` then gave approximately 1 MB/s. On an 80 MB profile on an `rclone mount` of Cloudflare R2, the first overview page takes 2 s to 5 s. Before, it took 66 s. On other file systems, the read does not change.
- On macOS, xprof-rs also finds a FUSE mount, for example `macfuse`, and it reads each file in order.
- The HLO text writes each shape directly into the output, and it does not decode the shape of an instruction two times. Threads write the parts of a large computation at the same time. On a 280 MB TPU v4 profile with 4 cores, `get_hlo_text`, `get_hlo_module_content` and `get_graph_viewer` take 0.24 s. Before, they took 0.57 s. The text does not change.
- For the CLI commands that read the op profile, xprof-rs makes the values of the op profile directly. Before, it made the JSON text of the op profile and then read the text again. On a 280 MB TPU v4 profile with 4 cores, `get_hlo_op_profile` and `get_top_hlo_ops` take 0.61 s, and `get_profile_summary` takes 0.56 s. Before, they took 0.76 s, 0.75 s and 0.73 s. On an 80 MB profile, the times do not change.
- The steps of a TPU read only the operation metadata that the op lines use, and threads read them at the same time. The steps add the self time of each category by a number, not by the text of the category in a sorted map. On a 1.7 GB profile with 4 cores, `get_overview` takes 5.7 s (before: 6.3 s). On a 280 MB TPU v4 profile, it takes 0.65 s (before: 0.67 s).
- The HLO modules parse at the same time as the op statistics, and the fused children wait for them only at the end. Before, the op statistics waited for the modules at the start. On a 280 MB TPU v4 profile with 4 cores, `get_hlo_op_profile` and `get_top_hlo_ops` take 0.57 s (before: 0.60 s).
- The op statistics sort the operations of each step by small keys, and they find the stats of an operation by a table. Before, they compared the name of each stat. On a 280 MB TPU v4 profile with 4 cores, `check_host_boundness` takes 1.02 s. Before, it took 1.15 s.
- The parse finds the roles of each event metadata one time. It does not look up a name that is longer than the longest known name.
- The check of an HLO proto examines the nested messages of a large message at the same time. It finds the rule of a field in a table. On a 280 MB TPU v4 profile with 8 cores, the check takes 17 ms (before: 103 ms). The first `overview_page` request takes 0.55 s (before: 0.62 s).
- Each metadata entry keeps the result of the check of its HLO proto. Before, one cold request for op statistics checked the same proto four times. On a 280 MB TPU v4 profile, this removes 0.35 s of CPU time from the first `overview_page` request.
- The parse of a profile reads the metadata of each plane on all cores. It reads the stats of an event metadata in the same pass as its name. On a 280 MB TPU v4 profile with 8 cores, the parse takes 39 ms (before: 52 ms).
- The op statistics find the program sums of each operation once for each plane. Before, they found them again for each operation in each step. On a 280 MB TPU v4 profile, this removes 0.15 s of CPU time from the first `overview_page` request.
- The stack frames of the trace viewer copy a text only when they keep it. Before, they copied each long name and HLO text twice before they removed the copies with the same text.
- A cached response for a client without gzip decodes its parts of 1 MiB on all cores. On a 280 MB TPU v4 profile with 8 cores, the warm `trace_viewer` response takes 16 ms (before: 53 ms).
- The CLI command `aggregate_xplane_events` joins the durations of each event name on all cores. Before, one thread joined the durations of all names.
- The CLI writes a JSON list of more than 4096 items in parts on all cores. On a 280 MB TPU v4 profile with 8 cores, the cold `aggregate_xplane_events` command takes 325 ms (before: 365 ms).
- The `op_profile` tool keeps the JSON text of each subtree as a part, and then joins all parts one time on all cores. Before, each level of the tree copied the text of its subtrees again. On a 280 MB TPU v4 profile with 8 cores, the first `op_profile` request with `group_by=provenance` takes 0.78 s (before: 0.86 s). It uses 1.29 GB of memory (before: 1.48 GB).
- To find the thread pool regions, xprof-rs reads the names of the event types one time, and it compares the bytes. Before, it checked the text of each long name three times. On a 280 MB TPU v4 profile with 8 cores, the first `memory_profile` request takes 147 ms (before: 158 ms).
- The trace viewer sorts its events in time buckets, in parallel. Before, one sort of all events moved each event many times. The order of the events does not change. On a 1.7 GB profile with 8 cores, the first trace viewer request takes 9.0 s, not 12.1 s. Its CPU time is 47 s, not 63 s. On a 280 MB TPU v4 profile, the time does not change, and the peak memory decreases from 1.11 GB to 0.92 GB.
- The trace viewer gives the levels of a very large track faster. Each level is a pass over the events of the track. These passes now run at the same time, and each pass stays a part behind the pass before it. The levels do not change. On a 1.7 GB profile with a track of 20 million events, the first trace viewer request takes 8.2 s, not 8.9 s.
- After the sort, the trace viewer numbers the equal events, the async tracks and the flows in parallel parts. It also puts the events of all tracks in one array, not in one vector for each track. The ids do not change. On a 1.7 GB profile with 8 cores, the first trace viewer request takes 7.7 s, not 8.3 s.
- When xprof-rs puts the events in groups, it finds the parent of each nested event in parallel chunks. Before, one loop on one thread read all events of a line. The groups do not change. On a 1.7 GB profile with a line of 20 million events, the first `memory_profile` request takes 2.01 s, not 2.18 s.
- The parser checks the order of the events of each line, sorts them, and moves their times in parallel. Before, a line with many events used one thread. The events do not change. On a 1.7 GB profile, the first `memory_profile` request takes 1.94 s, not 1.98 s.
- xprof-rs makes the names of the event groups in parallel, after it gives the groups to the events. Before, it made each name on one thread while it gave the groups. The names do not change. On a 1.7 GB profile, the first `memory_profile` request takes 1.79 s, not 1.93 s.
- To connect the producers and the consumers of the events, xprof-rs sorts one list of all links in parallel. Before, it put the links in a hash map on one thread, and then sorted the map. The edges do not change. On a 1.7 GB profile, the first `memory_profile` request takes 1.69 s, not 1.78 s.
- The event groups fill their lists of edges without a copy of the offsets. On a 1.7 GB profile, the first `memory_profile` request takes 1.66 s, not 1.70 s.
- The memory profile releases its parsed profile on a separate thread after the response, as the other tools do. On a 1.7 GB profile, the first `memory_profile` request takes 1.53 s, not 1.67 s.
- The memory profile decodes its memory events in parallel. On a 1.7 GB profile, the first `memory_profile` request takes 1.40 s, not 1.51 s.
- The cost analysis of an HLO module with a graph that two `async-start` instructions call is now linear in the number of instructions. Before, each instruction read the full log of calls again. For an entry graph with 30,000 instructions, the analysis takes 0.12 s. Before, it took 0.57 s.
- The megascale stats keep the result of each instruction search, also when the HLO module does not have the instruction. Before, the search read all the instructions of the module again for each event of an instruction that it did not find. The output does not change.
- With a remote log directory, a request for a session that the mirror has does not list the full store again. Before, such a request listed all the folders of the store each 5 s, and an error in any folder gave "502 Bad Gateway".
- The trace viewer frees the events of each line of a profile after it converts them. Before, it kept all of these events until the end of the conversion. On a 1.7 GB profile with 8 cores, the first request of the trace viewer uses 9.4 GB of memory. Before, it used 13.2 GB. The request takes 7.5 s. Before, it took 7.4 s.
- To make the derived lines of a TPU, xprof-rs keeps 40 bytes for each event. Before, it kept 96 bytes and the tags of the event. Few events have their own tags, thus a map keeps them. On a 1.7 GB profile with 8 cores, the first request of the trace viewer takes 7.1 s. Before, it took 7.3 s. During this step, the memory falls from 8.2 GB to 7.0 GB.
- The trace viewer reads the links of an event without link stats from its metadata one time for each line. Before, it read the stats of each event again. On a 1.7 GB profile with 8 cores, the first request of the trace viewer takes 6.6 s and 46.6 CPU seconds. Before, it took 7.0 s and 50.1 CPU seconds.
- The op statistics of the host decode the stats of a large host line on all cores. Before, one thread decoded all the events of the line. On a 1.7 GB profile with 8 cores, the first request of the op profile takes 3.0 s. Before, it took 3.2 s.
- For the busy time of the TPU chips, an op interval that starts in the interval before it joins that interval. Before, the op statistics kept each op interval until the end. On a 1.7 GB profile with 8 cores, the first request of the op profile uses 4.4 GB of memory. Before, it used 5.5 GB. The overview page uses 4.4 GB. Before, it used 5.7 GB.
- On Linux, xprof-rs maps a profile file of 16 MiB or more on a local file system. Before, it copied the file into its memory. A read lease keeps the mapped bytes valid. Before another process writes or truncates the file, xprof-rs makes a private copy of the bytes. On a 1.7 GB profile with 8 cores, the op profile uses 2.8 GB of memory, and the trace viewer uses 7.7 GB. Before, they used 4.4 GB and 9.3 GB.
- The trace viewer keeps 64 bytes for each event. Before, it kept 72 bytes. A table keeps the device and the resource of each track, and one byte keeps the entry and the category of a flow. On a 1.7 GB profile with 8 cores, the first request of the trace viewer takes 6.4 s and 43.9 CPU seconds. Before, it took 6.6 s and 46.1 CPU seconds. The memory falls from 7.7 GB to 7.1 GB.
- The old `trace_viewer` tool and `check_host_boundness` find the cut of a trace with more than 5,000,000 events in one pass. Before, they read all the events four times. A sorted sample of the times gives a small range, and the pass keeps only the times in that range. On a 1.7 GB profile with 8 cores, the old trace viewer takes 4.7 s and 27.9 CPU seconds, and `check_host_boundness` takes 4.9 s. Before, they took 5.3 s and 29.5 CPU seconds, and 5.1 s. The output does not change.
- The old `trace_viewer` tool copies the parts of its JSON text into the response on all cores. Before, one core copied approximately 1 GB on a 1.7 GB profile. On that profile with 8 cores, the response takes 4.6 s. Before, it took 4.8 s. The CPU time does not change.
- The old `trace_viewer` tool writes the times of the events as Python `repr` does, without a new text for each number. On a 1.7 GB profile with 8 cores, the response takes 4.4 s and 26.5 CPU seconds. Before, it took 4.7 s and 28.8 CPU seconds. The output does not change.
- At the end of its build, the trace viewer keeps the events of each level in one list. It also frees the order of the tracks and the levels of the events earlier. Before, it kept a second copy of the lists for a short time. On a 1.7 GB profile, the memory at the end of the build goes down from 7.1 GB to 6.0 GB. The peak memory of the build does not change, and the output does not change.
- When the trace viewer gives the levels of the events, it keeps the kind of each event in the byte of its level. Before, a copy of the times of each track also had the kind, and each copied event used 24 bytes, not 16 bytes. On a 1.7 GB profile with 8 cores, the first request of the trace viewer uses 6.7 GB of memory. Before, it used 6.9 GB. The time and the output do not change.
- The protobuf reader reads a varint of at most 8 bytes with one load. The times of the events are varints of 6 to 8 bytes. On a 1.7 GB profile with 8 cores, `get_hlo_stats` uses 9.4 CPU seconds, and `list_xplane_events` uses 5.7 CPU seconds. Before, they used 9.7 and 6.1 CPU seconds. The output does not change.
- The trace viewer asks the system for huge pages for the events of a large trace. Thus the first writes take fewer page faults, and the later reads take fewer misses of the address cache. The sort of the events uses at most 256 time ranges, not 1024, so that the huge pages do not increase the memory. On a 1.7 GB profile with 8 cores, the first request of the trace viewer takes 5.8 s and 39.7 CPU seconds. Before, it took 6.3 s and 43.5 CPU seconds. The memory and the output do not change.
- The old `trace_viewer` tool frees the planes of the profile before it writes the JSON text. The text uses only the events that the tool takes from the planes. On a 1.7 GB profile with 8 cores, the response uses 6.3 GB of memory. Before, it used 7.7 GB. The time and the output do not change.
- The old `trace_viewer` tool keeps the arguments of each event in a sorted list. Before, it kept them in a tree map, and each small map used a full tree node. On a 1.7 GB profile with 8 cores, the response uses 6.2 GB of memory. Before, it used 6.5 GB. The output does not change.
- The derived lines of a TPU keep the parse of the texts of each metadata. Before, each event looked up its texts in a map of strings. On a 1.7 GB profile with 8 cores, the derived lines of a TPU take approximately 370 ms, not 490 ms. The first request of the trace viewer uses 38.9 CPU seconds. Before, it used 40.0 CPU seconds. The output does not change.
- The derive of a TPU sorts its events with a merge sort. The events of each line are usually in order, and the merge sort uses these runs. On a 1.7 GB profile with 8 cores, the sort of a plane with two such lines takes approximately 15 ms, not 260 ms. The first request of the trace viewer takes 5.45 s and 38.7 CPU seconds. Before, it took 5.68 s and 39.1 CPU seconds. The keys are different for all events, thus the output does not change.
- The trace viewer keeps 56 bytes for each event, not 64 bytes. An event keeps the index of its flow in 32 bits. It does not keep its serial, because the trace viewer finds the serial from the index of the event. On a 1.7 GB profile with 8 cores, the first request of the trace viewer uses 6.0 GB of memory and 37.7 CPU seconds. Before, it used 6.6 GB and 38.7 CPU seconds. The output does not change.

### Documentation and benchmark

- The README shows the times of all the CLI commands that need only a session.
- The README compares XProf and xprof-rs on tmpfs, on a disk, and on Cloudflare R2.
- `examples/benchmark.py` does warmup trials that it does not count, and then the trials that it counts. The trials of XProf and of xprof-rs alternate. Each cell shows the mean and the standard deviation. A mark shows a standard deviation of more than 10% of the mean. The option `--json` writes the values of all trials to a file.
- `examples/benchmark.py` shows the peak memory of XProf and of xprof-rs for each tool and each command. The value is the peak resident memory of the process that the system gives when the process stops. The options `--tools` and `--commands` select a part of the tools and of the commands, for example for a large profile.
- `examples/benchmark.py` has the option `--timeout`. A cold request or a cold command that takes longer stops, and its row shows the limit with a mark. The script does not measure that row again.
- `examples/benchmark.py` has the option `--memory-limit`. A server or a command that uses more resident memory stops, and its row shows the limit with a different mark. The script does not measure that row again.
